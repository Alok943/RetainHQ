## D-002 — Physics KC-graph granularity + Hinglish authoring policy (2026-07-05)

**Decision:** The NCERT Physics 9-10 knowledge-component graph targets a **150–250 KC honesty band**, not a padded-to-match number — final came in at 126 KCs / 140 prereq edges / 8 cross-year (Class-9→10) edges. Lesson prose splits by register: **hook/mental-model/explanation in Hinglish, but technical terms, formulas, `recall_hint`s, and `oa_questions` answers stay in English.**

**Why:** The research inputs (ALEKS/KST) suggested 300–500 concepts per multi-year course, but that figure is for a *full* course; padding NCERT Physics 9-10 to match would recreate the Cognitive Tutor over-practice failure the same research flagged (6,000+ KCs → students over-drill trivial nodes). Hinglish-for-teaching mirrors how Indian physics teachers actually teach (explain in Hinglish, board work in English) and keeps the *testable claim* — what an FSRS card actually quizzes — aligned with what CBSE boards demand in English.
**Tradeoffs / rejected:** Rejected matching the source research's 300–500 figure literally. Rejected full-Hinglish content (drills the wrong target for board exams) and full-English content (loses the pedagogical win of native-language explanation for Tier 2/3 students).

## D-003 — Physics interactive 3D scope: R3F concept simulators, not a game engine (2026-07-07)

**Decision:** 3D is scoped to exactly **6 concept families** (`orbit`, `magnetic-field`, `fleming-rule`, `em-induction`, `dispersion-prism`, `longitudinal-wave`) via React Three Fiber, lazy-loaded so non-3D lessons never pull in Three.js. Explicitly **not** applied to graphs, circuits, numericals, or mirror/lens ray diagrams (the existing 2D SVG renderers stay). Each scene follows **Predict → (optional Manipulate) → Observe → Reflect**, reusing the app's existing predict-before-reveal UI rather than a parallel prediction system; manipulation is per-scene opt-in (discrete choices only, no sliders), not mandatory. Every scene's physics lives in a pure `computePhysics(params) → derived` function, separate from the Three.js render — **no formula/binding DSL in the lesson JSON**, formulas stay in code.

**Why:** Unity/Unreal were considered and rejected for a mobile-first (₹8–12k Android) product: Unity WebGL ships a 10–30MB runtime with no data-driven content contract; Unreal has no browser export path at all (Pixel Streaming needs a GPU server per session). R3F hits the quality ceiling that matters for teaching (clean, smooth, correctly-lit) at a fraction of the cost, and a photorealistic Earth actively *hurts* learning by pulling attention off the force vector. The litmus test for scope ("if a scene isn't predictable/changeable, it's not thinkable — keep it 2D") prevents 3D becoming decoration.
**Tradeoffs / rejected:** Rejected a JSON `formula:`/`bindings:` mini-language (would mean shipping an expression evaluator into the runtime). Rejected mandatory manipulation on every scene (extra state/UI/mobile-frame cost for no guaranteed learning gain). Rejected designing the primitive library for Chemistry/Math/DSA now — DSA already has its own 2D execution-trace renderer and is a different paradigm; generalize only when a second subject actually needs it.

## D-004 — Tests section: production-formats-first, one-way FSRS bridge, redemption lap (2026-07-10)

**Decision:** The Tests section defaults to **production-format questions** (fillup, numeric, code-output, code-fix, code-write, query-write) — MCQ is capped at ≤20% of a bank and allowed only when JEE-grade (multi-step reasoning, distractors that are worked-out wrong answers tagged with a named misconception). ~25%+ of questions carry a `trap: true` flag (an engineered wrong-but-obvious answer) with a `trap_note` explaining it on reveal. Grading is deterministic client-side for every type except `fillup`, which is the **one** LLM call (`grade_fillup`, gated on `GRADER_ENABLED`, canonical-answer-grounded). **FSRS bridge is one-way**: a `wrong`/`missed` test outcome pulls an *existing* due review forward (`apply_fsrs(..., RATING_AGAIN)`) only if the node already has an `Activity`+open `Review`; a `got` outcome never touches FSRS, and a test never creates a new card. One **redemption lap** (retry only the wrong/missed questions) runs at the end of a session as practice — it never changes the submitted score or the FSRS bridge.

**Why:** Recognition-based testing (MCQ) is the weakest form of retrieval and lets students "win" by pattern-matching a keyword — the user's explicit push-back mid-session. The one-way FSRS rule ("one brain, two sensors") stops the quiz from becoming a second competing scheduler: it can only pull a review date *closer*, never push it out from a lucky guess or a different recall format than the review itself uses. The redemption lap gives the honest within-session repeat (practice) without letting same-session re-quizzing measure short-term memory and inflate scores.
**Tradeoffs / rejected:** Rejected the original ask of multiple full passes with shuffling *within* one session (measures short-term memory, not learning — FSRS already owns spaced re-testing). Rejected letting `got` outcomes extend FSRS intervals (would let one lucky/different-format correct answer overwrite a card's real schedule). Scoring is a pure function (`got`=+10, +15 with a trap bonus, `missed`=0, `wrong`-non-MCQ=0, `wrong`-MCQ=−5 guess penalty) — `missed` and non-MCQ `wrong` score identically so honesty never costs more than a guess.

## D-005 — query-write test grading needs a fully isolated PGlite instance (2026-07-10)

**Decision:** Added `pgliteRunner.runIsolatedSql(sql, schemaSql)` — a bare PGlite instance seeded with *only* the test question's own `schema_sql`, no canonical dataset. `Tests.jsx`'s `gradeQuery` uses this, not the existing `runSql(sql, setupSql)`.

**Tradeoffs / rejected:** Rejected reusing `runSql`'s existing throwaway-DB path as-is — it looked isolated (fresh `PGlite()` instance per call) but wasn't schema-isolated.

## D-006 — School roadmap browsing: Class → Subject → Chapter from the phase-naming convention (2026-07-10)

**Decision:** School users get a dedicated `SchoolRoadmaps.jsx` (Class 9/10 → Subject → Chapter), replacing the career-catalog `Roadmaps.jsx` page entirely when `audience==='school'`. It derives Class and Chapter by **parsing the existing `RoadmapNode.phase` string** ("Class 9 · Motion" → class "Class 9", chapter "Motion") — no new backend field or migration. A step auto-advances when it has exactly one option (today: one subject, Physics, so Subject is invisible until Chemistry/Math exist). Picking a chapter navigates into the existing `RoadmapDetail` page with a new `location.state.expandOnlyPhase`, which collapses every *other* phase so the chapter reads as its own page.

Routing school users to their own page removes that failure mode structurally (it can't recur for any future school roadmap either) rather than patching the fallback. Parsing the phase string instead of adding a `class`/`subject` column keeps the data model unchanged and lets Chemistry/Math slot in for free as long as their content follows the same "Class N · Chapter" phase convention.
**Tradeoffs / rejected:** Rejected fixing only the `roadmapDomains.js` fallback (would leave school users on career-page vocabulary/grouping generally, not just the header). Rejected a dedicated per-chapter route (`/roadmaps/:id/chapter/:phase`) — reusing `RoadmapDetail` with a collapse-all-but-one nav-state was cheaper and kept one source of truth for the phase list UI.

## D-007 — JSONB model columns must carry a SQLite variant for the test suite (2026-07-10)

**Decision:** Any `models.py` column using Postgres `JSONB` must be declared via the shared `_JSONB = JSONB().with_variant(JSON(), "sqlite")` variant (see `TestAttempt.results`), not raw `JSONB`. Postgres behavior is unchanged; the variant only swaps to plain `JSON` under SQLite.

**Why:** The tenant-isolation suite (`backend/tests/`) runs `create_all()` against in-memory SQLite (fast, no Supabase needed). A raw Postgres-dialect `JSONB` column makes SQLite's DDL compiler crash at schema creation, killing **all** tests at collection — this is exactly how the audit-generated suite shipped 14-for-14 red. The variant is the one-line convention that keeps the suite runnable as new JSONB columns are added.
**Tradeoffs / rejected:** Rejected pointing the suite at a disposable Postgres (testcontainers/Supabase branch) — heavier setup for a solo repo, and SQLite already exercises the WHERE-clause isolation logic the suite exists for. Known limit (noted in the suite): Postgres-only SQL paths (`array_agg`, `auth.users` in dashboard/admin bodies) can't run on SQLite and stay uncovered until a disposable-Postgres run exists.

## D-009 — Progress-safe roadmap re-seeding: upsert by title, never delete (2026-07-10)

**Decision:** A roadmap seed that runs against a roadmap with **live user progress** must be a progress-preserving upsert, not the default delete-and-recreate. `seed_python_swe.py` was rewritten to: (1) match existing nodes **case-insensitively by `lower(title)`** and `UPDATE` them in place (phase/section/tier/order_index and title) so the row's `id` never changes; (2) `INSERT` only genuinely new titles; (3) **never delete** — titles in the DB but absent from the seed are reported, not removed; (4) upsert the `roadmaps` row (`ON CONFLICT (id)`) instead of deleting it. The seed file's titles are authoritative and are refreshed onto the matched row.

**Why:** `user_progress.node_id → roadmap_nodes.id` is `ON DELETE CASCADE`, and the original seed did `DELETE FROM roadmap_nodes … + re-INSERT with fresh uuid.uuid4()`. Re-running it to add nodes regenerates every node UUID and **silently cascade-wipes all of that roadmap's user progress** — the exact failure the "add without losing progress" constraint named. Matching must be case-insensitive because live node titles were Title-cased while the seed file was sentence-cased; an exact match would miss every existing row, insert duplicates, and orphan the originals (cascading their progress). The whole run is one `engine.begin()` transaction, so an interrupted attempt (the Supabase pooler dropped connections repeatedly this session) rolls back with zero writes. Verified runs: `18 inserted, 130 updated, 0 removed` then `0 inserted, 148 updated, 0 removed`.

**Tradeoffs / rejected:** Never-deleting means a node genuinely removed from the seed lingers in the DB until cleaned up by hand (reported at run end) — accepted so progress loss is structurally impossible for additive edits. Rejected keeping the fixed-UUID delete+reinsert pattern (fine for a brand-new roadmap, catastrophic for one in use). The other ~32 seeds still use the destructive pattern — see BACKLOG.

## D-010 — Cross-roadmap lesson reuse: copy files + align seed titles; `kind` by runnability (2026-07-10)

**Decision:** When a new/expanded roadmap overlaps an existing one (python-backend reusing python-swe's Python-language lessons; python-swe's new Phase 2.5 reusing python-backend's concurrency lessons), reuse is done by **copying the lesson JSON into the target roadmap's content folder** (retargeting `roadmap`/`slug`/prereq+unlock edges) and **aligning the seed node titles to the existing lesson titles** — never editing the shared lesson's title. Lesson `kind` is chosen by whether the topic is meaningfully Pyodide-runnable: concurrency / async / threading lessons are **`engineering`** (illustrative, non-executed snippets); stdlib / file-I/O / regex are **`concept`** (runnable `code_walkthrough`), matching python-swe's existing all-`concept` convention.

**Why:** Node→lesson resolution keys on the node title (exact title, then `slugify(title)` against the per-roadmap manifest — `RoadmapDetail.jsx:lessonSlugForNode`), so a node only links to a lesson whose title/slug it matches. Editing a shared lesson's title to fit one roadmap would break resolution in the other; copying keeps each roadmap folder self-contained (the manifest is per-roadmap). `engineering` for concurrency because threading/multiprocessing/asyncio can't execute meaningfully in Pyodide (no OS threads/processes; browser event-loop limits) — forcing them into the runnable `concept` shape would ship broken walkthroughs.

**Tradeoffs / rejected:** Copying duplicates lesson JSON across folders (drift risk if one copy is later edited) — accepted because the pipeline treats each roadmap folder as the unit and there's no shared-lesson abstraction. Rejected editing the existing lessons' titles to match the seed (explicit user directive: reuse existing lessons, align the seed instead). Systemic gotcha surfaced: node titles and lesson titles must agree (case-sensitively on the exact-match path) or the lesson silently shows no "Learn" button — 30 older python-swe nodes were unlinked purely from sentence-vs-Title casing.

## D-011 — Lesson renderer stays a bespoke 3-block prose format; content contracts must not use markdown fences (2026-07-10)

**Decision:** Extended (not replaced) the existing lesson-prose renderer (`RichText` in `frontend/src/LessonView.jsx` + `linkifyGlossary` in `frontend/src/lib/glossary.jsx`) to also support `- `-prefixed bullet lists and single-backtick inline code chips, on top of its existing paragraph / indented-code-block split. The renderer still does **not** parse markdown syntax (no ` ``` `-fenced code blocks, no `#` headers) — every roadmap's `PROMPT-*.md` content contract was updated with the exact three-block grammar (blank-line-separated prose / 2-space-indented code / `- ` bullets) so authors don't reach for markdown fences by habit.

**Why:** A live bug was found and fixed mid-session: ~42 already-authored `python-swe` lesson files used ` ```python ` fences in `overview.what` (the natural markdown habit), which the renderer's code-block detector (every line must start with whitespace) doesn't recognize — it silently fell through to a plain `<p>`, collapsing the whole snippet plus its literal ` ``` ` markers into one run-on line. The 42 files were fixed after the fact, but the durable fix is upstream: state the grammar explicitly in every contract so the bug class can't recur as the other 8 roadmaps run their own format-upgrade pass.

**Tradeoffs / rejected:** Rejected teaching the renderer to also parse ` ``` ` fences defensively (papers over the contract violation instead of preventing it, and adds markdown-parsing surface to a renderer kept deliberately minimal). Rejected adopting a full markdown library — the 3-block grammar covers everything lesson content needs (prose, code, bullets, inline code) with no new dependency.

## D-012 — Every lesson must inline-flag its own sharp edges, even when a later lesson owns the deep dive (2026-07-10)

**Decision:** Added rule 28 to `content/PROMPT.md` (and the equivalent to all 9 other roadmap `PROMPT-*.md` contracts): every lesson's teaching body must flag the topic's real-world traps with a short example, even when the full treatment belongs to a later lesson in the same roadmap — closing with an explicit "covered fully in `<slug>`" pointer to a topic already listed in that lesson's own `metadata.unlocks`. `PROMPT-lesson-critic.md` now checks for this (and for the D-011 formatting grammar) in its Phase 2 pass.

**Why:** Triggered by a real product gap the user surfaced from a live Python-tutor chat: Sonnet correctly explained that slicing a list is a shallow copy — a fact `lists.json` itself never taught, even though the roadmap graph already listed `shallow-vs-deep-copy` as something `lists` unlocks. The AI tutor was smarter than the lesson content it was supposedly teaching from, undermining the "the lesson is the source of truth" model the retention engine is built on.

**Tradeoffs / rejected:** Rejected leaving traps solely in the later, dedicated lesson (defers the fact past the point a learner actually hits it — the trap fires while using the earlier concept, e.g. `a[:]` looking safe). Rejected fully re-teaching the deep-dive topic inline instead of flagging it (bloats every lesson and duplicates a lesson that already exists) — the rule caps a flag at one short example + 1-2 sentences + the forward pointer.

## D-013 — Large content-QA passes: verify findings against file content directly, not against subagent self-reports (2026-07-10)

**Decision:** Running a multi-batch lesson-critic pass over ~117 reformatted `python-swe` files, 3 of 9 background critic-agent batches (33 files) silently failed with zero recoverable output when the orchestrating process exited mid-task — the harness's own notification said only "failed," with 0-byte output files and no partial transcript. Rather than re-launching those batches, Claude read and critiqued the 33 files itself in-session, patching real defects directly (11 of 33 needed fixes). Separately, asked to confirm the earlier 9 batches' ~26-29 flagged NEEDS-WORK files had been fixed, Claude did not trust its own prior summary — it re-read the actual current file content for each flagged defect and found **none** of them had been applied, plus a new regression: an unrelated prior pass had "fixed" a mojibake character in `shallow-vs-deep-copy.json` by truncating two recall-questions mid-sentence instead of repairing them.

**Why:** Background subagent batches can lose work invisibly on process exit, and a critic's own "PASS/NEEDS-WORK" verdict is not the same as the finding being *fixed* — nothing had actually applied any of the first 9 batches' fix lists despite them having been reported as found. For content-quality work at this scale, verifying against the real file before reporting status is the only way to avoid compounding an already-stale claim.

**Tradeoffs / rejected:** Rejected re-dispatching the 3 failed batches as fresh subagents (repeats the same silent-failure risk and still needs the same verification step afterward) — direct, synchronous review is slower but leaves nothing unverified. Rejected treating "critic ran and reported a verdict" as equivalent to "fixed" for status reporting going forward.

## D-014 — C++/Java language roadmaps: reuse `kind:"engineering"`, prose+code (no runtime), design-doc replaces deep-research (2026-07-10)

**Decision:** C++ (`cpp-swe`) and Java (`java-swe`) language-roadmap lessons reuse the existing `kind:"engineering"` validator branch (teach-from-scratch prose + a required `code_snippets` list) rather than a new kind. There is no in-browser C++/Java runtime, so lessons are prose + **≥2 hardcoded, annotated, never-executed** code snippets. For a *language* roadmap a well-defined design doc (`content/PROMPT-cpp.md`, carrying a per-node misconception map) **replaces the DSA-style Gemini deep-research step**. Generate **one Step per handoff packet, pilot Step 1 first**; algorithmic CP nodes (segment/Fenwick tree, DSU, LRU) are authored prose-first and tagged `[trace-later]` for a future viz pass. C++ seed gained `const-correctness` + `iterator-invalidation` nodes.

**Why:** `engineering`'s field contract already fits language lessons exactly (annotated code + prose), so no validator/renderer work is needed — roadmap and kind are independent. Deep research earns its keep for DSA because it supplies fabrication-prone facts (engineering examples, interview frequency); language semantics (RAII, move, `equals`/`hashCode`) are canonical and in-distribution, so a pitfall-dense design doc suffices — *provided* it carries the per-node misconception (the anti-hallucination anchor). Batch-by-Step because long-horizon generation degrades and, worst for a language, fabricates APIs.

**Tradeoffs / rejected:** Rejected a new `language` kind (needless validator+renderer work; `engineering` fits — the historical kind name stays semantically odd but the fields are exact). Rejected a deep-research run per language phase (canonical knowledge; the design doc substitutes). Rejected whole-roadmap one-shot generation (thinning + API fabrication).

## D-017 — Syllabus-upload roadmaps: frontier model, review-before-commit, per-user rows in the same tables (2026-07-11)

**Decision:** The "Bring Your Own Path" feature (PDF syllabus → personal roadmap) is built as:
- **One model call** (`services/syllabus.py`) taking the raw PDF as a document/inline part (vision path) with a JSON schema — no client-side text extraction, no Groq. The provider is **routed by `SYLLABUS_MODEL`**: a `gemini*` id calls Google (`google-genai`), anything else calls Anthropic (`claude-opus-4-8`). Both send the identical prompt + schema, so switching providers to compare extraction quality/cost is a config change (Gemini Flash-Lite wired in 2026-07-11 to A/B against Opus).
- **Two-step review-before-commit API**: `/api/syllabus/extract` returns a draft and saves nothing; the user edits it in the UI; `/api/syllabus/commit` persists it. The draft is never auto-saved.
- **Personal roadmaps are ordinary `roadmaps`/`roadmap_nodes` rows** with a new nullable `roadmaps.user_id` (NULL = official catalog), inheriting the creator''s `audience`, `slug` NULL (route by UUID). Visibility = catalog-by-audience + own; personal roadmaps resolve only for their owner.
- The extraction prompt forces **decomposition into atomic, testable topics** (capability-phrased titles), because node granularity determines whether logged activities and their FSRS cards stay sharp.

**Why:** Reusing the existing tables means `Activity.node_id`, the log form''s roadmap picker, progress, blockers, and the whole FSRS loop work with zero changes — the feature is purely additive. A frontier model is justified because extraction is one-shot, user-visible, and low-volume (guarded by a 5/user/day limit + 10 MB cap); quality of the parse is the product. Review-before-commit exists because an LLM syllabus parse is ~90% right and silently persisting the wrong 10% erodes trust.

**Tradeoffs / rejected:** Rejected a separate `custom_roadmaps` table (duplicates the graph machinery for nothing). Rejected client-side PDF text extraction (breaks on scanned/table syllabi; the model''s vision path handles both). Rejected auto-generating prerequisite edges in v1 (LLM-guessed edges would pollute the "Why am I stuck?" diagnosis; sequential order carries enough structure). Deletion nulls activity links instead of cascading them — review history is the user''s memory data and outlives the roadmap.

## D-019 — Review questions: persisted reusable sets, topic-grounded for roadmap cards, explicit depth choice (2026-07-12)

**Decision:** Question mode moves from generate-per-request to a persisted `question_sets` table. A set is generated ONCE per card (+depth), stored as `[{question, reference_answer}]`, served SHUFFLED for at least `QUESTION_SET_REUSE` (=2) review sessions, then regenerated. Grounding splits by card type: **node-linked cards** (e.g. syllabus roadmaps) are TOPIC-grounded — the node title+description is the contract, standard textbook knowledge of that topic is fair game, key_memory only biases; **free-form cards** keep key_memory as sole ground truth. The generator writes a `reference_answer` per question at generation time; grading judges against the stored reference (injected server-side, never sent to the client). The user explicitly picks revision depth ('main' = 2-3 core Qs, 'deep' = 4-5 incl. apply/derive/edge-case) via a Review-screen toggle remembered in localStorage. Grader model: `openai/gpt-oss-120b` (probe showed `llama-3.1-8b-instant` produced repetitive, under-specified questions).

**Why:** Persistence amortizes the LLM cost (~1 generation per 2+ sessions instead of per view), keeps the quiz stable while a memory is forming, and the shuffle stops answer-order memorization. Topic grounding fixes the "key memory serves nothing for roadmap cards" problem: an exam grades you on the syllabus topic, not on whatever you happened to write down. Reference answers written at generation time are what make persistence + strict grading possible without a user rubric.

**Tradeoffs / rejected:** Rejected regenerating every session (cost + churn). Rejected sending reference answers to the client (leaks the answer key pre-attempt). Rejected auto-detecting depth from FSRS state in v1 (explicit user choice is the ask; adaptive depth can come once metrics exist). times_used increments on serve (not on grade), so an abandoned session burns a use — acceptable, guarantees "at least two" without double-count bookkeeping.

## D-025 — `duration_ms` on `reviews`, measured client-side via `performance.now()` (2026-07-13)

**Decision:** `reviews.duration_ms` (nullable int) is stamped by the frontend as `performance.now()` at card-show minus `performance.now()` at outcome-submit, sent in the `/complete` POST body, and clamped server-side to `(0, 1_800_000]` — anything outside that range persists as NULL rather than rejecting the completion.

## D-031 — Career Coach Phase 1: event log over in-place mastery, `node_id` FK over `topic_ids[]`, `entity_id` dedupe from day one, scheduler deliberately absent (2026-07-19)

**Decision:** Four bundled calls from `docs/SPEC-career-coach-phase1.md` §10, all executed as specced:
1. **Event log, not in-place mastery.** `learning_events` is an immutable append-only log; `node_mastery` is a derived cache, fully rebuildable from the log alone (`services/evidence.recompute_node`/`recompute_user`).
2. **`node_id` FK instead of the parent design doc's `topic_ids[]` array.** Phase-1 producers (review completions, manual log) each map to exactly one node.
3. **`entity_id` dedupe (partial unique index `(user_id, source, entity_id) WHERE entity_id IS NOT NULL`) shipped from day one**, not added later when a polling producer needs it.
4. **The FSRS-style scheduler is deliberately not built this phase** — no Today screen, no confidence probes, no coach agent.

**Why:** (1) An event log lets any future mastery formula (including a learned/vectorized one) be re-run as a pure computation over history, never a data migration — the *event log* being correct matters more than the *weights* being correct, since weights stay config-tunable (`evidence_weights.py`) forever. (2) A real FK gives referential integrity and cheap joins now; multi-node events (if a future producer ever needs them) land in a `payload.topic_ids` key without touching the fold, and the column can become a join table later without a rewrite. (3) Polling producers (LeetCode/GitHub, phase 2+) re-read the same source row repeatedly — a double-counted event silently inflates mastery, which is the failure mode most likely to destroy trust in the number (design doc Philosophy #3: "mastery may understate; it must never overstate"). Building the guard now, while there are only two producers, is cheap; retrofitting it once there are six is not. (4) The scheduler is the highest-trust-risk component in the parent design doc (§10) and needs its own golden-scenario test suite — building it against a mastery model not yet validated on real data would mean debugging two unknowns (the formula and the scheduler) at once.

**Tradeoffs / rejected:** The event-log approach costs more storage and a recompute path to maintain forever, and makes mastery a two-step read (`m_learned × retrievability` at read time, not a single stored number) — accepted, since Design law 2 (mastery is a derived cache) is the whole point of doing this phase first. `topic_ids[]` was rejected only for *this* phase; it's the documented escape hatch the moment a producer needs multi-node events. No scheduler this phase means Career Coach ships with zero user-facing surface beyond the `/evidence` debug page — accepted per the parent spec's own phasing rule (§17: additions require a removal).

## D-032 — Evidence fold: two independent running totals (capped vs. uncapped), not one shared total, to make the T3-exposure-cap order-independent (2026-07-19)

**Decision:** `services/evidence.fold_events` maintains two separate compounding accumulators — one folding only T1/T2 ("uncapped") evidence, one folding only T3/`CONTENT_CONSUMED` ("capped") evidence, each via the same single-step update formula (`m ← m + w·(1−m)`, clamped) — and reports `m_learned = max(uncapped, capped)`. The spec's own §4.2 pseudocode instead describes a single shared running total with an inline clamp (`if capped and m_learned_after > 0.35: m_learned_after = max(m_learned_before, 0.35)`).

**Why:** The spec's §8 test suite requires a specific invariant (test 10): replaying a T1 event and a T3 event in either order must land on the same `m_learned` — "the T1 value." Working the single-shared-total pseudocode by hand shows it does **not** satisfy this: if the capped event is folded *first* (while the shared total is still low), its small contribution survives uncapped, because the compounding formula `m + w·(1−m)` uses whatever `m` already is — there's no way for a later event to retroactively discover that an earlier small bump came from a since-superseded capped source. Folding T1 first and T3 second passes (the clamp catches it), but folding T3 first and T1 second does not (order-DEPENDENT, contradicting what the test demands). Two independent streams combined by `max()` are provably order-independent for this exact reason: each stream's own compounding is invariant to interleaving with the other, since neither stream ever reads the other's running value.
**Discovery method:** not caught by inspection — found by writing test 12/10-equivalent unit tests against the literal pseudocode during implementation and watching the two orderings diverge (0.376 vs. 0.350 for a concrete hard/none-pass + one CONTENT_CONSUMED example), then re-deriving the two-stream design and re-checking it against the same concrete numbers before generalizing.

**Tradeoffs / rejected:** The two-stream design still satisfies the two isolated tests the spec's pseudocode was clearly aimed at (T3 alone converges to exactly 0.35; a single T3 event on a node already above 0.35 never drags it down) — those hold under either design. Rejected: literal single-shared-total pseudocode (fails order-independence, as shown above); adding two new persisted columns to `node_mastery` (`m_uncapped`/`m_capped`) to make a true O(1) incremental update possible — the spec's own `node_mastery` schema (§2.2) has no such columns, and `record_event`'s "incremental" step instead replays that one node's full history via `recompute_node`, which is exactly equal to the pure fold by construction and costs nothing at this scale (a single user's per-node event count is bounded to dozens, not millions).

## D-033 — Career Coach Phase 2: tree = personal roadmap, `node_meta` sidecar, templates-not-invention, diagnostic writes ordinary events, soft-detach, quota-exempt daily rate limit (2026-07-19)

**Decision:** Six bundled calls from `docs/SPEC-career-coach-phase2.md` §11, all executed as specced:
1. **A career tree is a personal roadmap, not a new entity.** `POST /api/career/tree/commit` writes to the same `roadmaps`/`roadmap_nodes`/`roadmap_node_prerequisites` tables `syllabus.py`'s upload flow already uses (`roadmaps.user_id` set, `audience='career'`).
2. **`node_meta` is a sidecar table**, not new columns on `roadmap_nodes` — `stable_key`/`priority`/`est_effort_min`/`subject`/`user_edited` live there, keyed by `node_id`, one row only for career-tree nodes.
3. **`services/career_tree.py` adapts a versioned template; it never invents one from scratch.** The template is always in the model's prompt as ground truth; §3.3's hard rules (no invented subject keys, ≤10 new `custom.`-prefixed nodes, no cycles, ≤90 nodes total) are enforced in Pydantic validation after the call, with one retry then an unmodified-template fallback — never an error screen.
4. **The diagnostic writes ordinary `RECALL_GRADED`/`T2_verified_internal` `learning_event`s** via the same `services/evidence.record_event` every other producer uses, replayed at `/tree/commit` time (after the nodes they target exist) — no separate "cold-start mastery" code path.
5. **Node deletion is a soft detach.** `DELETE /api/career/nodes/{id}` nulls `learning_events.node_id` (with a `payload.detached_from_stable_key` marker) and `activities.node_id` before deleting the `RoadmapNode` row itself — confirmed at this migration that neither FK carries `ondelete=CASCADE`, so a raw delete without the nulling step would be rejected by Postgres, not silently cascade away the immutable event log.
6. **Career-tree generation is quota-exempt** (doesn't touch `user_prefs.custom_roadmaps_created`, the syllabus-PDF lifetime cap) **and daily-rate-limited instead** (`CAREER_TREE_DAILY_LIMIT=3`/user/day, in-memory — same pattern as `routes/syllabus.py`'s extraction limit).

**Why:** (1) Free evidence-engine/FSRS/lesson-runtime reuse on day one — the single biggest reason phase 2 was sequenced after phase 1 rather than before it. (2) Keeps the shared catalog table (used by the school platform and every other roadmap) unwidened for one feature's fields. (3) A curated, versioned syllabus stays reviewable/diffable — the model personalizes within a bar a human set, matching parent design law that a generic tree the user edits always beats an error screen. (4) Direct consequence of phase 1's fold-only design (Design law 2) — there is no other mastery path to keep in sync. (5) Design law 2 (evidence survives) outranks referential tidiness — the same principle phase 1 established, now exercised by a second producer (tree edits) instead of just time. (6) Career-tree generation is the primary onboarding path; a lifetime cap would gate the main flow the way it's meant to gate PDF-upload abuse specifically.

**Tradeoffs / rejected:** (1) `roadmaps` now serves three purposes (catalog, syllabus-upload, career-tree) — every query against it needs consistent `user_id`/`audience` filtering discipline, a cost accepted for the reuse payoff. (2) One extra join (`node_meta` ⋈ `roadmap_nodes`) on every career-tree read. (3) Three curated templates (backend/ai_engineer/sde_generalist) is a real, ongoing content-authoring cost and caps role coverage until more are written. (6) Nothing else rejected here — quota-exemption was the only reasonable call once (4)'s onboarding-path framing is accepted.

## D-034 — Commit needs staged `flush()` boundaries, not one `add_all()`-then-`flush()`, because none of the new mapped classes have an ORM `relationship()` between them (2026-07-19)

**Decision:** `POST /api/career/tree/commit` stages its writes into three explicit `flush()` boundaries — `Roadmap` alone, then `RoadmapNode` rows, then `NodeMeta`/`RoadmapNodePrerequisite`/the `CareerGoal.roadmap_id` update together — instead of adding everything to the session and flushing once at the end (still one transaction; `commit()` only happens once, at the very end, so atomicity per the spec's test 9 is unaffected).

**Why:** SQLAlchemy's unit-of-work only knows to order one mapped class's INSERT before another's INSERT/UPDATE when there's an ORM `relationship()` connecting them. `CareerGoal.roadmap_id`, `RoadmapNode.roadmap_id`, and `NodeMeta.node_id` are all bare FK columns with no `relationship()` declared (matching the rest of `models.py`'s style — this codebase generally doesn't declare back-populating relationships for simple FK links). Without a declared relationship, the unit-of-work has no dependency edge telling it "the goal's `roadmap_id` UPDATE must happen after the `Roadmap` INSERT" or "`node_meta`'s INSERT must happen after its `RoadmapNode` exists" — so a single `add_all()`-then-`flush()` can send them in either order.
**Discovery method:** not caught by `pytest` — the SQLite test database used by the whole suite doesn't enforce foreign-key constraints the way Postgres does, so all 171 backend tests stayed green through two live-Postgres failures in a row (`career_goals_roadmap_id_fkey` violation, then the identical `node_meta_node_id_fkey` violation one flush-stage later) — found only by walking the actual onboarding flow in a browser against the real local backend, per the repo's own verify-before-claiming-done convention.
**Tradeoffs / rejected:** Rejected declaring ORM `relationship()`s between `CareerGoal`↔`Roadmap` and `NodeMeta`↔`RoadmapNode` to let the unit-of-work order things automatically — would fix this specific ordering problem but is a bigger, precedent-setting style change across a codebase that otherwise treats these as plain FK columns everywhere else; the explicit staged-flush is a narrower, more obviously-correct fix scoped to the one function that needs it. Worth revisiting if a third such ordering bug turns up elsewhere.

## D-035 — Career templates ship as a backend-owned synced copy, not read from `content/` directly, because Render's backend build context excludes it (2026-07-19)

**Decision:** `content/career-templates/*.v*.json` stays the canonical authoring + CI-validated location (matching every other content file's convention), but `services/career_tree.py` reads templates from `backend/app/data/career_templates/` — a literal, checked-in copy kept in sync by a new manual script, `sync_career_templates.py` (run by hand whenever a template changes, before deploying; no build hook runs it automatically). **Why:** Both `SPEC-career-coach-phase2.md` (§3.1: templates live in `content/career-templates/`) and `SPEC-career-coach-phase1.md`'s CLAUDE.md-derived convention assumed the backend could read `content/` directly at runtime, or that the deploy topology would somehow make it available — neither spec author appears to have checked the actual Docker build context against the Render root-directory setting. A checked-in synced copy is a smaller, fully reversible, zero-deploy-risk fix.

**Tradeoffs / rejected:** Two copies of the same content must be kept in sync by hand — a template edit that forgets the sync script silently ships stale content with no error (there's no drift-detection check today). Rejected changing Render's root directory to the repo root (fixes the root cause, but is an infra change with real risk to an already-working prod deploy, made without the owner's explicit go-ahead — flagged instead of executed). Rejected fetching `content/career-templates/` over HTTP from wherever the frontend's synced copy is served (adds a network dependency + latency to every template lookup for a handful of small, rarely-changing JSON files — strictly worse than a local file read).

## D-036 — Diagnostic probes are selected round-robin per subject, and template content changes ship as new immutable version files (2026-07-20)

**Decision:** Two calls from `docs/SPEC-career-templates-v2.md`:
1. **`GET /api/career/diagnostic` selects its 8 probes round-robin across subjects** (template order; best-probe-first within a subject; deterministic), replacing a flat priority sort.
2. **Template content changes ship as new `*.v2.json` files; `*.v1.json` stays frozen.** `list_templates()` resolves the latest version per role, so new goals get v2 automatically; committed v1 trees are untouched because nothing re-reads a template file after commit (`template_version` on the goal is pin metadata only; pre-commit, `GET /diagnostic` deliberately loads latest). Removed nodes' stable_keys are retired, never reused.

**Why:** (1) The flat sort was subject-blind: Python's stable sort breaks priority ties by file order, so a template whose early subjects are foundational fills all 8 slots before later subjects get one — concretely, the AI Engineer diagnostic asked 8 math/classical-ML questions and zero LLM/GenAI questions, so a user who'd already built RAG apps had their entire GenAI subtree cold-started `unexposed` and got weeks of already-mastered work assigned. Round-robin guarantees subject spread by construction, making every future template safe without the author gaming file order. (2) Immutable version files are the parent design doc's own §6 law; the practical payoff is that a content fix never mutates what an existing user's pinned tree was built from, and rollback is "delete the new file."

**Tradeoffs / rejected:** Round-robin means a subject's 2nd-best probe can beat another subject's about-to-be-cut 1st-best on raw priority — accepted; spread is the point, and priorities still order probes *within* each subject. Rejected weighted-by-subject-priority sampling (needs randomness or fragile weights; determinism matters because a mid-diagnostic refresh must serve the same set). Rejected editing v1 files in place ("only one real user so far" was tempting but sets the wrong precedent the week before there are two). Also recorded: the spec's own verification step (create a throwaway goal, run the live diagnostic) was deliberately skipped — creating any goal archives the owner's real active goal via the one-active-goal partial unique index and there is no un-archive endpoint; verified against the synced runtime artifact by direct function call instead, and flagged "goal switch back" as a phase-3+ UX gap.

## D-038 — Six-layer learning-system architecture adopted; inference is hypothesis, evidence is fact (2026-07-21)

**Decision:** Adopted `docs/ARCHITECTURE-learning-system.md` as the canonical layer stack: Evidence (append-only `learning_events`) → Knowledge Graph (closed `roadmap_nodes` vocabulary, one graph, no parallel ontologies) → Learner Inference (all derived, one weights fold, every inference carries confidence/evidence_count/version) → Selection (a query; asymmetry rule — may add/advance/reorder, never remove/delay a due card on inferred strength) → FSRS (per-card, untouched, never fed invented history) → Review Experience (user grades, LLM diagnoses). Top law: no irreversible decision from inferred knowledge; postponed inferences (transfer coefficients, auto-delay, activation scheduling, confusion, propagation) graduate only via shadow-mode measurement, whose logging starts day one.

**Why:** Three specs (career-coach phase 1 "T4 never moves mastery", phase 3 "scheduler never overrides FSRS", LeetCode-retention §5.0 asymmetry rule) had each independently derived the same law; converged design discussion (2026-07-21, external LLM review agreeing on all six rejection points: concept-level FSRS, delay-from-inference, multiple accumulators, LLM-generated ontology, LLM grading, unexplainable readiness %) confirmed the stack. Stating it once above the phase specs prevents each new spec re-deriving — or accidentally violating — it. New material canonized beyond existing specs: evidence-is-fact/inference-is-hypothesis as the top law, inference self-certainty requirement, and explainability ("why this card, now?") as a ship-gate for selection logic.

**Tradeoffs / rejected:** Rejected editing the career-coach phase specs to host this (they are implementation records; rewriting shipped specs to say things they didn't say muddies history — the parent design doc is external to the repo anyway). Rejected concept-level scheduling entirely (FSRS fits per-item; blended observations degrade stability silently). Accepted cost: one more living doc to keep honest; mitigation is that it owns only laws, never implementation detail, so it should change rarely.

## D-039 — User-data tables are guarded against `TRUNCATE` at the DB level; content tables may never cascade into user history (2026-07-26)

**Decision:** Ten tables holding irreplaceable per-user history (`activities`, `reviews`, `question_sets`, `user_progress`, `learning_events`, `node_mastery`, `test_attempts`, `metric_events`, `career_goals`, `user_prefs`) carry a `BEFORE TRUNCATE … FOR EACH STATEMENT` trigger that raises. Emptying one of them now requires dropping its trigger in an explicit migration. Migration `a9d4f7c2e618`.

**Why:** On 2026-07-26 every user's `activities` and `reviews` rows vanished, and Home rendered the brand-new-user state with all stats at zero. Forensics ruled out both suspects: no migration deletes those rows, and `pg_stat_user_tables` showed `n_live_tup=0` while `n_tup_del` sat unchanged at its historical 7/8 — a table emptied without incrementing the delete counter is TRUNCATE, nothing else. The blast radius matched the transitive FK closure of `TRUNCATE problems CASCADE` exactly (`problems → {problem_concepts, concept_cards}`, `concept_cards → activities`, `activities → {reviews, question_sets}`), and every table outside that closure survived. The trap: `activities.concept_card_id` (added days earlier by `37714df921de`) is `ON DELETE NO ACTION`, which reads as safe — but `TRUNCATE … CASCADE` ignores referential actions entirely and empties every referencing table regardless. A re-import of a bulk-rebuildable content catalog therefore drained the one thing in the system that cannot be rebuilt from files. Postgres fires `ON TRUNCATE` triggers for cascade-added tables too ("first those listed in the command, and then any that were added due to cascading"), so a raising trigger on the *user-data* side aborts the whole statement — which is why the guard goes there.

**Tradeoffs / rejected:** Rejected dropping the `activities.concept_card_id` FK as the fix — it removes one bridge but not the class of bug, since `activities.node_id` and `user_progress.node_id` are the same kind of edge from `roadmap_nodes` and the ~32 roadmap seed scripts all rewrite content tables. Rejected relying on convention/docs alone (this incident *was* the convention failing). Accepted cost: an intentional truncate of these tables now needs a migration — deliberately more friction than a one-liner, which is the point. The guard is Postgres-only DDL in a migration, so the SQLite test suite (which builds via `SQLModel.metadata.create_all`, not Alembic) is unaffected. Note this is prevention only — it does not recover the lost rows; recovery is a Supabase point-in-time restore, and the incident's real lesson is that no backup/restore runbook existed to reach for.

## D-040 — Backups are self-hosted (nightly encrypted `pg_dump` in GitHub Actions), and the backup job doubles as the data-loss alarm (2026-07-26)

**Decision:** `.github/workflows/backup-db.yml` takes a nightly custom-format `pg_dump` of the `public` schema, verifies it with `pg_restore --list`, GPG-encrypts it (AES-256, `BACKUP_PASSPHRASE`) and stores it as a 90-day artifact on the private repo. `auth.users` is dumped data-only as reconciliation reference, explicitly *not* as a drop-in restore. The same job asserts that five critical tables are non-empty and fails the run if any is zero. Procedure, gaps and recovery playbook: `docs/RUNBOOK-backup-restore.md`. Supabase Pro was **not** purchased.

**Why:** D-039's incident was survivable in principle and unrecoverable in practice — the project is on the Supabase free plan, which has neither daily backups nor PITR, so there was literally nothing to restore from and ~100 activities and ~427 reviews across 19 accounts are permanently gone. Doing nothing until the next incident was not an option, and $0 was the constraint that had already been applied elsewhere (D-037 dropped the Anthropic key on cost). The DB is ~15 MB, so a logical dump is seconds and cents; GitHub Actions already hosts two scheduled workflows (`reminders.yml`, `keep-alive.yml`), so this adds no new infrastructure or vendor. The canary is the more important half: the incident went undetected until Home visibly rendered the new-user state, and nothing in the system would have noticed a table hitting zero. A daily zero-row check is crude but would have caught this exact failure the next morning.

**Tradeoffs / rejected:** Accepted up-to-24h data loss (snapshots, not PITR) and a single point of failure — the dumps sit in the same GitHub account as the code. Both are documented in the runbook as named gaps rather than quietly absorbed; offsite copies (R2/B2 free tier) and Supabase Pro (~$25/mo, real PITR) are the two upgrades, and Pro becomes the honest answer once the user base is more than people the founder knows. Rejected `supabase db dump` via CLI (another dependency for the same `pg_dump` call). Rejected storing plaintext dumps and relying on repo privacy alone — the artifact holds every user's email, so encryption is not optional even on a private repo, and the passphrase is explicitly required to live in a password manager outside GitHub. Known sharp edge, called out in both the workflow and the runbook: `pg_dump` cannot run through the app's transaction pooler (`:6543`) and the direct host is IPv6-only (GitHub runners are IPv4), so the **session** pooler (`:5432`) is the only URI that works — the workflow hard-fails on the two wrong ones instead of producing a broken dump. **Neither the backup nor the restore has been executed yet**; the workflow is committed but its secrets are unset, and the restore drill is unrun — until both happen this is a plan, not a backup.

## D-041 — Career Coach Phase 3 scheduler: pure derived plan, FSRS non-interference as a tested law, sprint beats balance, and an evidence floor added mid-implementation (2026-07-26)

**Decision:** `services/planner.py`'s `build_plan()` is a pure function (no DB, no clock, no randomness) that assembles a day's plan from reviews (FSRS-owned, untouched), frontier study nodes (prereq-gated, priority×urgency×unlock-weight scored), and at most one balance nudge. No `day_plans` table exists — the plan is always recomputed from `learning_events`/`node_mastery`/`career_goals` on `GET /api/career/today`, never stored. Three precedence rules, each pinned by its own golden scenario in `tests/test_planner.py` (G1-G10, 2 property tests × 50 seeds): (1) reviews always precede study items, in FSRS's own order, never reordered/dropped (G2/G9/G10 — the asymmetry rule, `ARCHITECTURE-learning-system.md` §0/§5.0); (2) a pinned sprint node wins slot 0 over a promoted balance item, which takes slot 1 instead (G5) — an explicit user declaration outranks an inference; (3) **the balance nudge is gated by `BALANCE_MIN_WINDOW_MINUTES=120`** (a trailing-21-day floor on total logged minutes, added during implementation — not in the parent spec), below which `balance={}` unconditionally and no `kind='balance'` item is ever produced (G1/G4b).

**Why:** Item 3 is the one worth explaining, because the literal spec rule breaks on its own most important user. With zero logged time, `a_s=0` for every subject, so `balance_s = 0 - p_s`, and the *most negative* subject is simply the one holding the largest share of the tree's priority — every brand-new user's very first plan would open with "dsa is under-served: 0% of your time vs 32% of your plan," a `-0.15` trip that fires from having done nothing, not from neglect. That is exactly the class of harm `ARCHITECTURE-learning-system.md` §0/D-038 already names: an inference must not drive a user-visible recommendation before it has evidence behind it. 120 minutes across 21 days is a low bar chosen to stop gating within roughly a week of real use, not a tuned value — it ships as a named constant alongside the rest of §7's untuned defaults, same status as everything else pending the ≥2-weeks-dogfood gate (§9 step 0; blocked today by D-039 truncating `learning_events` to 1 row).

A second correction, found while implementing sprint-vs-balance: a literal reading of "find the subject with the most negative `balance_s`, then check it isn't the sprint's subject" means that when the sprint's own subject genuinely *is* the worst-off one, **no** balance item fires for anyone — the sprint's subject has to be excluded from the candidate pool *before* the argmin, not checked after, or the doc's own G5 requirement ("a different neglected subject is still flaggable") is unsatisfiable. Implemented that way; the alternative (literal single-argmin) was rejected as a bug, not a design choice.

**Tradeoffs / rejected:** Rejected storing the plan (`day_plans` table) — a stored plan can drift from the mastery/review state that produced it and would need its own invalidation logic; recomputing from three already-authoritative tables is more code at read time but zero invalidation surface, mirroring D-038's "layer 3 is a derived cache" law one level up. Rejected letting `target_date` urgency reorder or truncate the study set relative to the open-ended plan: as specified, `urgency` multiplies every frontier node's score by the *same* factor, so it can never change relative ordering or which items get truncated at `MAX_STUDY_ITEMS=5` — G3 (`test_g3_crunch_vs_open_ended_never_drops_reviews_or_higher_priority_study`) passes today, but only because a plan-wide multiplier is structurally incapable of doing anything else; flagged in the implementation report as the constant/formula most likely to need a real per-node urgency term once dogfood evidence exists. Also flagged: `BALANCE_FLAG_THRESHOLD=-0.15` is a share, so it's structurally biased toward the tree's single largest subject — measured against the three shipped v2 templates, only one subject per template (`dsa` at `p_s=0.317` in `backend.v2`, `genai_engineering` at `0.170` in `ai_engineer.v2`, `dsa_core` at `0.263` in `sde_generalist.v2`) can *ever* trip it, even at zero logged time; every other subject (7-9 per template, all `p_s≤0.17`) is structurally unflaggable no matter how neglected. Not changed — reported per §11.2 of the implementation doc for the owner to decide with the numbers in hand, same as the rest of §7.

## D-043 — Companion chat-content consent ships as a popup choice screen with static-manifest + optional-permission gating, not the spec'd dynamic content-script registration (2026-07-26)

**Decision:** Chat-content classification (LLM-surface capture beyond page titles) stays OFF until a one-time three-tier choice — `cloud` (Recommended, Gemini paid tier), `nano` (on-device, plumbing only), `titles` (no permission grant, no consent needed). The tap is the consent artifact: `metric_events`/`companion_consent` (`{tier, copy_version, surface}`), read back via `services/metrics.get_latest_consent_tier()` — no new column. Chosen from the popup, not on first LLM-surface visit as the parent spec's §6 originally wanted, because `chatgpt.com`/`claude.ai`/`gemini.google.com` moved out of required `host_permissions` (every install used to grant AI-chat-site access before any consent existed — the exact posture §6 was designed to avoid, and the single largest Web Store review risk). The LLM content script (`llm_metadata.ts`) is a **static** `manifest.json` `content_scripts` entry matching those three origins, which now live under `optional_host_permissions`; Chrome itself refuses to inject a content script into an origin the extension doesn't currently hold, so the guarantee ("no grant, no capture, of any kind") is enforced by the browser, not by how carefully `llm_metadata.ts` is written.

**Why:** The parent implementation doc specified the opposite mechanism — `chrome.scripting.registerContentScripts()` called from the popup's grant handler, with the manifest entry removed entirely. Implemented it exactly that way first. Building it then proved it doesn't work with this repo's toolchain: `@crxjs/vite-plugin` discovers which content scripts to bundle by scanning the manifest's static `content_scripts` array — a script referenced only from a `registerContentScripts()` call at runtime is invisible to that scan and is silently dropped from the production build (confirmed directly: `dist/` had no trace of `llm_metadata.ts` after building the dynamic-registration version, while every statically-declared adapter got its usual loader file). Reverted to a static entry, moved only the *origins* to `optional_host_permissions`, and verified the resulting behavior against Chrome's own documentation: a granted optional host permission is exactly what gates whether an already-declared static content script is allowed to run on that origin (the same mechanism Chrome uses for host permissions generally — including the well-documented "reload the tab to pick up a freshly granted permission" caveat, which applies here identically). This gives the identical browser-enforced guarantee the spec wanted, with *less* manifest surface than the spec'd version (no `scripting` permission needed at all) and, unlike the spec'd version, an extension that actually contains the file it's supposed to run.

**Tradeoffs / rejected:** The spec's core reasoning (host permissions on AI-chat domains must not be required at install, and must instead be requested from a user gesture on the popup's tier buttons) is unchanged and implemented as written — only the injection mechanism changed, not the trust model. Rejected keeping the dynamic-registration code once the build gap was found, since an approach that silently ships a non-functional content script is strictly worse than a documented deviation, even though the spec explicitly named the dynamic approach. Rejected trying to make crxjs discover the dynamic entry (e.g. a fake unreachable static reference just to force bundling) as needlessly fragile compared to the static+optional pattern, which is a normal, intentional Chrome extension idiom. Known gap, not addressed: a tab already open on an LLM surface at the moment permission is granted won't start being tracked until it's reloaded or navigated again — inherent to the static+optional pattern (and no better under dynamic registration, which also doesn't retroactively inject into open tabs without a separate `executeScript` call the spec didn't ask for). ## D-044 — The Companion extension ships to Firefox from the same `extension/src` tree, via a Promise shim for the await-chrome sites and a manifest-only post-build step, not a second bundle (2026-07-26)

**Decision:** One source tree, two build outputs. `manifest.json` declares both `background.service_worker` (Chrome) and `background.scripts` (Firefox) side by side — each browser reads the key it understands and ignores the other — plus `browser_specific_settings.gecko` (`id`, `strict_min_version: 140.0`, `data_collection_permissions.required: ["browsingActivity"]`) and `gecko_android.strict_min_version: 142.0`. New `extension/src/browser_api.ts` wraps the ~15 call sites that `await` a WebExtension API (`storage.local.get/set`, `permissions.request/remove/contains`, `runtime.sendMessage`), resolving to Firefox's native promise-based `browser.*` when present and falling back to Chrome's own promise-native `chrome.*` otherwise — every other call site (badges, alarms, `onMessage.addListener`) was left on plain `chrome.*` since those don't depend on a return value. `npm run build:firefox` runs the normal Chrome build, then a small Node script (`scripts/build-firefox.mjs`) copies `dist/` to `dist-firefox/` and patches only the manifest's `background` key — the bundled JS is reused byte-for-byte.

**Why:** `@crxjs/vite-plugin` is Chrome-oriented and, when given a manifest with both `background` keys, drops the unrecognized `scripts` key from its own output entirely — confirmed directly by building it and inspecting `dist/manifest.json`, which came back with only `service_worker`. This is the same class of bug D-043 hit with dynamic content-script registration: crxjs only understands the Chrome-shaped subset of the manifest schema it was built around, and silently omits anything else rather than erroring. Since the underlying JS bundle doesn't actually differ between the two targets — the same TypeScript compiles to the same output regardless of which manifest loads it — a second full Vite build would duplicate work to produce identical files; patching just the one manifest key that differs is both simpler and immune to crxjs's Firefox gaps, since it runs entirely after crxjs has already finished. The `await chrome.` risk is separate and came from Firefox's own documented behavior (checked against MDN): Firefox's `chrome.*` namespace exists specifically for Chrome-extension source compatibility and is callback-only — an `await`ed call with no callback resolves to `undefined` silently, not an error, which is the worst kind of cross-browser bug because nothing fails loudly to reveal it.

**Tradeoffs / rejected:** Rejected `webextension-polyfill` in favor of a ~25-line local shim — the polyfill's own MV3-service-worker compatibility is itself version-dependent, and layering one build-tooling uncertainty (crxjs + Firefox) on top of another (a third-party polyfill + MV3 service workers) seemed like avoidable risk for ~15 call sites that a small typed wrapper covers directly and can be unit-tested with the same hand-rolled `chrome` mock the existing consent tests already use. `strict_min_version` was raised from the doc's proposed `128.0` (the floor for `optional_host_permissions`, which the doc had verified) to `140.0` after `web-ext lint` surfaced a requirement the doc hadn't checked: Firefox has required `data_collection_permissions` on every new extension's manifest since 2025-11-03, and that key itself needs Firefox ≥140 (Android ≥142) — a full major version above the doc's number, for a reason unrelated to what the doc was solving for. Declared `browsingActivity` as the required data category (titles, domains, durations of the sites captured — matches this project's own manifest description almost verbatim) rather than a broader category like `websiteContent`, since no page content is ever captured. Not resolved here: real Firefox verification (install unpacked, sign in, confirm a session syncs, confirm the consent screen grants an origin) — this environment's browser tooling can't drive Firefox or read `about:debugging`, so this rests on `web-ext lint` (0 errors) plus the unit-test suite, not a manual click-through. The Firefox OAuth redirect URL is logged on first sign-in rather than guessed (it's derived from the extension/add-on id and differs from Chrome's), so it still needs a real Firefox load before it can be added to Supabase's allowed-redirect list.

## D-046 — Manual "I solved this" marks are a completion checkbox, never evidence: they write only `problem_attempts`, structurally cannot reach `learning_events`/`node_mastery`, and `T4_claimed` was rejected as still too much (2026-07-27)

## D-047 — Companion "Smart tracking" reads AI-chat text, splits one session into per-topic `learning_events` via transport-only `content` sibling field, and stays weight-0 by construction (2026-07-27)

**Decision:** `chat_extract.ts` (new) reads ChatGPT/Claude/Gemini DOM turns — user turns in full, assistant turns truncated to 300 chars, capped at 60 turns / 12,000 chars, code blocks stripped — gated by a **live** consent-tier re-check on every capture (not a one-time check at script load, since an already-injected content script keeps running after a mid-session tier downgrade until the tab reloads). `stitcher.ts` picks the most-complete snapshot across a session's segments rather than concatenating them (each snapshot is already a full read, not a delta). Content travels as `CompanionSessionIn.content` — a **sibling** of `payload`, never nested inside it; `payload` keeps `extra="forbid"` and gained no content field, so raw chat text structurally cannot land there even by accident. New `services/topic_segmentation.py` (one Gemini call, ≤5 topics, model-written labels — never verbatim chat spans) fans a content-bearing session into N `LearningEvent` rows, one per topic, `duration_min` split by the model's `share`. Every fanned row is still `event_type="TIME_BLOCK"`/`trust_tier="T3_observed"` — `evidence_weights.TIME_BLOCK_WEIGHT` is unconditionally `0.0` regardless of tier or fan-out, so more topics structurally cannot mean more mastery (asserted by `test_companion_sync_topic_fanout_never_moves_mastery`). Per-topic idempotency uses `uuid5(NAMESPACE_URL, f"session_id/topic_index")` as `entity_id` (deterministic across retries, distinct across topics); the daily 50-session rate limit switched from counting `LearningEvent` rows to counting a dedicated `companion_session_tracked` metric event per submitted session, so a session fanning into 5 rows still only costs 1 against the cap. Segmentation is gated to cloud-tier + ≥5 min duration + an LLM-origin source + a 3-content-sessions-per-batch cap, to bound worst-case sequential Gemini calls inside one request. Consent copy-versioning added (`CONSENT_COPY_VERSION`, currently `v2`): a tier stored under a stale copy version reads back as unset from `getConsentTier()`, re-prompting the user, because a v1 "Smart tracking" consent described materially less processing than what the tier does now.

**Why:** A single AI-chat session routinely covers several unrelated topics (a Postgres question, then a React bug), but pre-D-047 the whole session became one event attributed to whatever the chat happened to be titled after — usually just the first topic, since none of the three sites reliably retitle a conversation as it evolves. The transport-vs-payload split exists because `CompanionSessionPayload.extra="forbid"` is the load-bearing security invariant from D-043/SPEC-companion-phase1 §6 ("no raw chat content ever persisted") — content needed a path into the request that this invariant's own shape makes it structurally incapable of touching. Fixing `switchConsentTier`'s origin-grant/revoke decision to query `hasLlmOriginPermission()` live (rather than trust the caller's passed `currentTier`) was a bug found while implementing copy-versioning, not a pre-existing one: a v1 user re-prompted by the version bump would have their cached tier value read back as `null`, and the old code compared *that* against `'cloud'` to decide whether to revoke the origin grant — always false, so a genuine downgrade to `titles` would have silently left the LLM host permission dangling. Rate-limiting by a dedicated metric event (not `LearningEvent` row count) was chosen over the alternative of extracting `payload->>'session_id'` via Postgres JSONB `.astext` because the test suite runs on SQLite (`.astext` is Postgres-dialect-only SQL and would pass at query-construction time but fail at execution against SQLite) — the metric-event approach is dialect-portable and needed no schema change.

**Verification findings (same session, both fixed):** A review pass after the implementation — not the test suite, which passed throughout and encoded the same wrong assumptions the code did — surfaced two bugs in the interaction between content capture and the 15-min-checkpoint/20-min-kill split shipped earlier the same day. **(1)** `chat_extract.ts` returns the whole visible conversation on every capture, not a delta, so a 50-minute chat checkpointed every 15 minutes shipped three cumulative snapshots ("turns 1-6", "turns 1-12", "turns 1-18") and the backend segmented and recorded turns 1-6 three separate times — duplicate topic rows in the evidence log at 3x the Gemini cost. Fixed by letting only a genuinely CLOSED session carry content; a checkpoint flush now sends metadata only. **(2)** The root cause underneath it, and a latent bug in the checkpoint split itself that had nothing to do with content: `CHECKPOINT_MS` (15m) is *shorter* than `INACTIVITY_KILL_MS` (20m), so the "has been running ≥ 15 min" condition fired on a session whose activity had already stopped — clearing the buffer and destroying the trailing segments before the kill window could ever recognize them as closed, so that session never closed at all. With fix (1) applied this became visible as *zero* content-bearing syncs rather than three; without it, it had been silently mis-classifying every long session's final chunk as a checkpoint. Checkpointing now additionally requires recent activity (`CHECKPOINT_ACTIVITY_RECENCY_MS = 6m`, one 5-minute `EMIT_INTERVAL_MS` plus margin). Both fixes required moving the decision out of `service_worker.ts` — untestable in isolation because of module-level `chrome.alarms.create` and supabase-client construction — into a new pure `stitcher.planSync()`, now pinned by a 70-minute simulation test asserting exactly one content-bearing sync carrying the fullest snapshot. Separately hardened in the same pass: the sync-queue `storageLocalSet` is now try/caught with a strip-content-and-retry fallback, because content took a queued session from ~200 bytes to as much as 16KB and a full 300-session offline backlog can approach Chrome's 10MB `storage.local` quota — an unhandled over-quota rejection would have aborted the flush and silently stopped syncing forever, which is far worse than losing a topic split.

**Tradeoffs / rejected:** The closing session covers only the time since the last checkpoint, so the whole conversation's topics attach to that shorter duration (a 50-minute chat checkpoints at 15/15/15 and closes with 5 minutes carrying all the topics) — accepted deliberately: these are weight-0 `TIME_BLOCK` rows that cannot move mastery either way, so an understated duration is strictly better than the same topic credited three times. **Selector verification (2026-07-27, against live DOM — this is what the console check bought).** ChatGPT's `[data-message-author-role]` confirmed working. Claude's original `.font-claude-response` was **wrong in the most dangerous way available**: the reply body's class is `font-claude-response-BODY`, a different class token, and CSS matches tokens exactly — so it never matched a reply at all, and instead silently selected Claude's *thinking-block summaries* ("Pinpointed off-by-one loop initialization error…") plus the bare token `DSA_COACHING`, an internal project identifier. ## D-050 — LeetCode importer upsert must reconcile a problem's OTHER existing rows, not just write the one it's given; verify DB against the source file, not against invariants chosen after the fact (2026-07-30)

**Decision:** `import_leetcode_catalog.py`'s primary-concept upsert now runs `plan_stale_primary_cleanup()` before writing anything for a problem. The importer had always upserted on `(problem_id, node_id)` — correct for the row it's about to write, blind to every other row that problem already has. When a mapping's `primary` moves to a different node, or resolves to `out_of_scope`/a scaffold slug so no primary is written at all, the OLD row at the OLD node_id was simply never revisited and silently kept `role='primary'` forever. `plan_stale_primary_cleanup` is a pure function — `{node_id: role}` in, `(to_delete, to_demote)` out — so it's unit-tested (7 cases) without a DB or fixture files, and it's scoped deliberately to `role='primary'`: a supporting/alternative row the file no longer lists is left alone, since dropping it on absence would silently discard curation from an earlier mapping version the current file simply didn't restate.

**Why:** This is a real incident, not a hypothetical the reconciliation logic was written to pre-empt. Merging `mapping.v3-tail.json` (797 pass-3-reclassified rows) into `mapping.v1.json` and re-running the existing importer put three separate kinds of stale data into prod, discovered in three separate passes:

1. **311 problems with two `role='primary'` rows** — the problem's primary moved to a new node, so the importer inserted a fresh row and left the old one exactly where it was. Two primaries breaks the one-primary-per-problem invariant `learning_events.node_id` resolution depends on (`SPEC-leetcode-retention.md` §3.2.-1) — a solve event would double-count evidence across two concepts or pick one arbitrarily.
2. **34 problems with a primary pointing at a TEACHING-SCAFFOLD node**, after their mapping had moved to `out_of_scope` — the exact class of row this session's earlier scaffold-primary guard (import-time refusal to *write* a scaffold primary) was built to stop, surviving anyway because the guard only ever checks what's being written, never what's already there.
3. **82 more with a legal-but-stale primary** the file had since moved to `out_of_scope` — caught only by writing a direct DB-vs-file comparison script and finding zero mismatches in *either direction*, after two invariant checks chosen by hand (no duplicate primaries; no scaffold-node primaries) had both already passed clean.

That third find is the real lesson, independent of the specific bug: **"I checked an invariant and it passed" is not the same claim as "the data is correct."** The first two waves were caught, fixed, and reported as done — using invariants that happened not to cover the third failure mode. Only comparing the database directly against the file it's supposed to reflect — every problem, both directions — actually proved correctness, and it's what should have been reached for first rather than last. Re-running the fixed importer against prod a second time confirmed the property that matters: `0 removed, 0 demoted` — the upsert-plus-reconciliation is now genuinely idempotent, not merely upsert-idempotent.

**Tradeoffs / rejected:** Reconciliation is scoped to a problem's rows *at import time*, driven by whatever `mapping_data` the current run actually contains — a problem dropped from the mapping file entirely (not present in `mapping_data` at all, as opposed to present with `primary: out_of_scope`) is never visited and any existing rows for it are left untouched. Not a gap in this fix (no code path currently drops a problem from the file), but worth a `BACKLOG.md` line if that ever becomes possible. Considered writing the cleanup as a one-off SQL script instead (matching the earlier scaffold-fix pattern) and rejected it: a manual script fixes prod once and leaves the *importer* itself as broken as before, so the identical bug reappears on the next legitimate re-import — the fix has to live in the code path that runs repeatedly, not in a script that runs once. `mapping_version` was also hardcoded `"v1"` at all three ProblemConcept write sites regardless of the source file's actual version — fixed to read it from the file, since a merge like this one would otherwise have written the wrong provenance into every row it touched, defeating the "why did mastery move?" traceability `SPEC-leetcode-retention.md` §3.2.1 requires. ## D-051 — The interactive OAuth flow (`launchWebAuthFlow` + token parsing + `setSession`) runs entirely in the background script, never in the popup (2026-07-30)

**Decision:** `popup.ts`'s sign-in button now only sends `{ type: 'SIGN_IN' }` via `runtimeSendMessage` and awaits the response; `service_worker.ts` owns the whole flow — building the auth URL, calling `launchWebAuthFlow`, parsing the returned tokens, and calling `supabase.auth.setSession()` against its own client, which shares `chrome.storage.local` with the popup's client via the same custom storage adapter both already used.

**Why:** Confirmed root cause, not a guess — diagnosed from Supabase's own auth logs (`get_logs(service='auth')`) showing repeated successful server-side `Login` events (`login_method: oauth`, referer matching the extension's real `extensions.allizom.org` domain) with a burst of retried `/authorize` calls in between and no session ever reflected in the extension, then confirmed directly: loading the popup's `index.html` as a normal tab (`moz-extension://<uuid>/index.html`, sidestepping the popup's own transient lifecycle) let the identical code sign in successfully end-to-end (`/auth/v1/user` → 200). **Tradeoffs / rejected:** If the originating popup instance doesn't survive (the common case that caused this bug), its own success/failure message never gets consumed and the status line silently doesn't update — the user has to reopen the popup to see "signed in," rather than getting live in-place feedback. Accepted as a known gap rather than solved fully: the durable fix (state lands in shared storage regardless) matters more than the cosmetic one, and forcing a solution to the live-feedback problem (e.g. a broadcast message plus a persistent status banner independent of popup lifecycle) is real added complexity for a one-time onboarding action, not the everyday flow. This also **corrects an assumption in D-044's tradeoffs section**, which read the symptom as "the Firefox redirect URL still needs to be added to Supabase's allowed-redirect list" — the logs prove that URL was already accepted; the failure was entirely downstream of a successful `/authorize`. `launchWebAuthFlow` was moved, not `permissions.request()` (the tier-choice buttons) — that call's documented synchronous-user-gesture requirement is a different, narrower constraint than the popup-lifecycle issue fixed here, and it still runs from the popup unchanged. 75 extension tests unchanged and passing; `addons-linter` and `web-ext lint` both stayed clean (0/0/0) after the change.

## D-052 — `switchConsentTier` calls `permissions.request()` before any other awaited call, whenever the tier needs origins (2026-07-30)

**Decision:** `consent.ts`'s `switchConsentTier` now branches on `needsOrigins` (`newTier === 'cloud'`) *before* awaiting anything. When true, `permissions.request({ origins: LLM_ORIGINS })` is the first async call in the function, full stop — no `hasLlmOriginPermission()` check beforehand. `request()` is documented to resolve `true` with no dialog when the permission is already granted, so skipping that check costs nothing and buys gesture safety. `hasLlmOriginPermission()` (which awaits `permissions.contains()`) moved into the `else` branch, which never calls `request()` and so has nothing to lose by awaiting first — it's still used there for the same reason the removed check used it: deriving "does the browser actually hold this grant" from live permission state rather than the caller's possibly-stale cached tier (a v1-copy-version user re-prompted for consent has `getConsentTier()` return `null` even though the underlying browser grant is still live).

**Tradeoffs / rejected:** A regression test asserts call ORDER (`chrome.permissions.request` must be the first mocked call, before `contains` or `storage.set`) rather than asserting anything about gesture state directly — jsdom has no concept of a "user input handler," so call order is the only observable proxy for "nothing was awaited first." Verified the test is a real regression guard, not a tautology: stashed the fix, confirmed the new test fails against the pre-fix code (`expected 'contains' to be 'request'`) exactly as expected, then restored it. Considered checking `hasLlmOriginPermission()` first and only calling `request()` when actually needed (the original shape, just reordered to check-after-request via some other mechanism) — rejected as unnecessary complexity once it was confirmed `request()` itself already no-ops safely on an existing grant; removing the pre-check outright is simpler and inherently gesture-safe rather than gesture-safe-by-careful-ordering. 76 extension tests (up from 75); `addons-linter` and `web-ext lint` both stayed clean (0/0/0). ## D-053 — The LeetCode origin is requested at runtime from the popup, not assumed granted at install (2026-08-02)

**Decision:** The popup's "Import solved LeetCode problems" button now calls `permissions.request({ origins: ['*://*.leetcode.com/*'] })` as the first awaited call in its click handler, before sending `LEETCODE_BACKFILL`. The origin stays in `host_permissions` (it also gates the static `leetcode.ts` content script); the request is wrapped in try/catch so Chrome — which rejects `request()` for an origin not declared under `optional_host_permissions`, having already granted it at install — falls through unchanged. `service_worker.ts`'s backfill fetch also gained `credentials: 'include'`.

**Why:** Reported as two separate bugs (LeetCode not syncing live; backfill failing with "NetworkError when attempting to fetch resource") that turned out to share one root cause. Firefox MV3 does **not** grant `host_permissions` at install — MDN is explicit that host permissions are user-granted and that "if an extension update requests new host permissions, these are not shown to the user," so an install carried forward across updates can sit permanently ungranted with no prompt ever shown. Nothing in the extension ever requested the origin at runtime, because Chrome's install-time grant made that unnecessary and the Firefox port (D-044 onward) never revisited the assumption. Verified directly rather than inferred: `leetcode.com/api/problems/all/` returns **no `Access-Control-Allow-Origin` header at all** (`vary: Cookie, Authorization`, checked 2026-08-02), so without the host-permission CORS exemption the background fetch is blocked outright, not merely cookie-less — hence a thrown `TypeError` rather than a non-2xx. The same missing grant stops `leetcode.ts` injecting, which is why live solve capture failed alongside it. `credentials: 'include'` is a genuinely separate defect stacked underneath: cross-origin `fetch` defaults to omitting cookies, and this endpoint answers an uncredentialed request with `200` and `status: null` on every problem — so even a correctly-granted install would have reported "No solves found" rather than an error, which is exactly how the bug first presented.

**Tradeoffs / rejected:** Rejected moving the origin into `optional_host_permissions` so `request()` is legal on both engines — it would make Chrome's already-working content-script injection conditional on a grant that has never been asked for, trading a Firefox-only bug for a Chrome-only one. Rejected fetching from a `leetcode.com` content script (same-origin, cookies automatic, no CORS at all): it needs an open LeetCode tab, which the popup can't assume, and it still needs the same host grant to inject. The denial path only surfaces "Failed: LeetCode access denied" on the button for 3s — it does not link the user to `about:addons`, and live capture stays broken silently for a user who denies; a persistent "LeetCode access not granted" state in the popup body is the honest fix and belongs in `BACKLOG.md` rather than bolted on here. Note this is the third instance of the same Firefox gesture rule (D-051, D-052) — `permissions.request()` is first-await-or-nothing, and the discipline has to hold at every call site independently. 76 extension tests unchanged and passing; `tsc --noEmit` clean; `npm run build:firefox` clean.

## D-054 — The extension requests OUR OWN backend origin as a host permission; corrects D-053 (2026-08-02)

**Decision:** `API_ORIGIN_PATTERN` (derived from `API_BASE_URL`, new `extension/src/config.ts`) is requested via `permissions.request()` from the two gestures every user passes through: the consent-tier choice (`switchConsentTier`, **both** tiers) and the LeetCode import button. `switchConsentTier` now always calls `request()` — `['titles']` asks for the API origin alone, `'cloud'` for the API origin plus `LLM_ORIGINS` — and a denied grant no longer blocks the `titles` choice from being recorded.

**Why:** **This supersedes D-053's root-cause claim, which was wrong.** D-053 blamed the ungranted `*://*.leetcode.com/*` permission; the Firefox MV3 facts it cites are all correct, but the failing request was never the LeetCode one. Proven, not reasoned: pasting both fetches into the background console returned **200 for the uncredentialed AND the credentialed** LeetCode call, while the same handler still threw `TypeError: NetworkError`. By elimination that leaves the only other fetch in the block — the `POST` to `${API_BASE_URL}/api/evidence/leetcode/backfill`, i.e. our own API. `main.py` builds its CORS allow-list from explicit origins, and a Firefox extension's origin is `moz-extension://<UUID>` with the UUID regenerated per install, so the extension can never appear on that list by any configuration. **Tradeoffs / rejected:** Rejected loosening backend CORS to `moz-extension://*` — it would work, and every request still needs a valid ES256 JWT so it isn't an authz hole, but it grants *every* Firefox extension on a user's machine the ability to make browser-authenticated cross-origin calls to our API, and CLAUDE.md's "explicit allow-list, never `*`" exists to prevent exactly this class of reasoning. The host-permission route achieves the same outcome with the grant scoped to our extension alone. `credentials: 'include'` on the LeetCode fetch (added earlier this session) is **kept** — the console test proves it doesn't cause the failure, and it's independently required: without cookies the endpoint answers `200` with `user_name: ""` and every `status: null`, which the old code reported as "No solves found" and which is what sent this hunt down the wrong path to begin with. That signed-out shape is now detected explicitly and named. The `titles` tier's contract changed — it previously requested no origins at all, and `consent.test.ts` asserted that as a feature; the assertion was wrong, since `titles` uploads titles to the same API and was therefore a tier that captured locally and could never sync. The user-facing copy makes no "no permissions" claim (only the LLM-access claim, which still holds), so no copy version bump. Not fixed here: a user who denies the prompt gets no persistent explanation, and the `cloud`-denied path can't re-request the API origin alone because the gesture is spent — both left to the BACKLOG line D-053 already added. 77 extension tests (up from 76); `tsc --noEmit` clean; `npm run build:firefox` clean. **Untested against a live Firefox as of writing** — the reload-and-import verification is the next step, not a completed one.

## D-055 - The approach inferred from a user's code reframes questions; it never routes mastery (2026-08-02)

**Decision:** LeetCode-mode cards may carry the user's own pasted solution (`activities.solution_code`). Deliberately asymmetric.

## D-066 — NeetCode `external_id` masks CRC32 to 31 bits; the importer dry-run now flushes (2026-08-02)

**Decision:** `slug_to_external_id` returns `zlib.crc32(slug) & 0x7FFFFFFF`, and `import_neetcode_catalog.py`'s dry run calls `await db.flush()` before rolling back.

**Why:** Both found while auditing D-064. `problems.external_id` is a Postgres INTEGER (int4, max 2_147_483_647 — verified against prod), but bare `zlib.crc32` returns an unsigned 32-bit value up to 4_294_967_295. Measured against the real catalog: **453 of 938 slugs (48.3%) exceeded int4**, including ordinary ones like `binarySearchTree` and `hashTable` — so a `--commit` run would have raised `NumericValueOutOfRange` on roughly half the catalog.

The second fix is the more important one, because it is why the first bug shipped looking verified. D-064 recorded the importer as "verified end-to-end against the LIVE api and prod DB in dry-run mode", and the dry run genuinely did run clean — but it called `db.add()` and then `rollback()` without ever flushing, so **not one INSERT was ever sent** and no column constraint was exercised. It validated the fetch and the create/update split and nothing else, while reading as a full end-to-end check. Flushing inside the transaction now exercises every constraint for real; the rollback still guarantees nothing persists. Re-run after the fix: 938 INSERTs executed and validated against prod, then discarded.

**Tradeoffs / rejected:** Masking rather than widening the column to `bigint` — a migration on a live table shared with the 3,999-row LeetCode catalog, to accommodate a synthetic id this codebase invents, is the larger change for no benefit; 31 bits is ample for ~1k slugs and the existing collision check still runs against the real set. General lesson worth carrying: **a dry run that never writes is not a dry run of the write.**

## D-069 — Distribution zips are built by `scripts/package_zips.py`, never `Compress-Archive` (2026-08-02)

**Decision:** New `extension/scripts/package_zips.py` packages `dist-firefox/` and `dist-chrome/` into `submit/*.zip`, writing every entry name via `Path.as_posix()`. It then re-opens each archive and parses the RAW local-file-header bytes to assert no backslash and no hidden dot-entry, exiting non-zero if either appears. `companion-source.zip` stays on `git archive`, which already emits spec-correct names and includes exactly the tracked files.

**Why:** AMO rejected 1.2.3 twice. Windows PowerShell 5.1's `Compress-Archive` writes entry names using the OS path separator, so 27 of 30 entries were stored as `assetsoo.js`; ZIP APPNOTE 4.4.17.1 requires forward slashes. AMO reports only the FIRST offending entry, so the first rejection named `.vite/manifest.json` and — once D-068 removed that — the second named `assetsctivity_tracker-DX2XVkAx.js`, the new first entry. The whole archive was malformed both times; D-068's `.vite` strip was a real and necessary fix, but it was never the cause of the rejection.

**The diagnostic lesson is the load-bearing part.** The first rejection was assessed as "just AMO's error formatting" on the strength of a `zipfile.namelist()` check reporting zero backslashes — and that check was worthless, because **Python's `zipfile` normalizes backslashes to forward slashes on read**. The library reports a clean archive while the bytes on disk are malformed. Only parsing the local file headers directly exposes it, which is why the verification in this script does exactly that. Generalisation worth keeping: when validating an artifact against an external validator's complaint, read the artifact's bytes, not a library's interpretation of them — the library's convenience normalization is precisely what hides the class of bug the validator is objecting to.

**Tradeoffs / rejected:** Python rather than Node — Node has no stdlib zip writer, and hand-rolling a ZIP container or adding a dependency to package three files is worse than using the stdlib of a language this repo already builds on. Not wired into an npm script, because packaging is a release-time action rather than part of `build:firefox`, and `REVIEWER-BUILD.md` deliberately defines `dist-firefox/` (not the zip) as the reproducible artifact — so the zip step stays outside the reproduction path a reviewer follows. The hidden-dot-entry skip duplicates D-068's build-script strip on purpose: one is the fix, the other is the guard that fails loudly if a future build step reintroduces it.


## D-070 — The LeetCode import runs inside a leetcode.com tab, not in the service worker (2026-08-02)

**Decision:** `scanRecentSolves` no longer fetches anything itself from the background context. New `extension/src/background/leetcode_tab_fetch.ts` acquires a real leetcode.com tab — reusing an already-open one, otherwise opening a background tab it closes again afterwards — and satisfies each page request via `scripting.executeScript({ world: 'MAIN' })`. The injected function is three lines: fetch a URL with `credentials: 'include'`, return `{status, ok, body}` as raw text. New `scripting` permission. `scanRecentSolves`'s `fetchImpl` parameter lost its `= fetch` default and is now required.

**Why:** The import had never once succeeded. It failed with `LeetCode returned 403`, and the decisive measurement was running the identical request from the page's own console:

```
page console    GET /api/submissions/?offset=0&limit=5  ->  200 + JSON
service worker  the same URL, same cookies, host permission granted, `credentials: 'include'`  ->  403
```

`/api/submissions/` returns the full **source code** of every submission, so LeetCode guards it far more tightly than `/api/problems/all/` — which the pre-D-060 import used and which answers a background fetch happily. That difference is why the endpoint swap in D-060 (needed for the language/date filters, which `/problems/all/` cannot support) silently traded a working import for a broken one. No header could have fixed it: `Referer` is a forbidden header name that no extension can set, and an extension-initiated request is cross-site for SameSite cookie purposes. The context itself is what's rejected, so the fix is to stop using that context.

Borrowing the page makes the fix correct **by construction** rather than by guessing which header was missing — the injected `fetch` runs in byte-for-byte the same context that returned 200 in the console test.

**Tradeoffs / rejected:**
- *Keeping the scan logic in the page:* rejected. Only transport is injected; the cutoff, language filter, stop conditions and earliest-solve-wins rule all stay in `leetcode_backfill.ts`, pure and unit-tested. Nothing that decides *what gets imported* runs inside a page we don't control, and the existing tests kept applying unchanged.
- *`declarativeNetRequest` header rewriting to fake a `Referer`:* rejected. It needs another permission, is a guess at the actual check, and does nothing about SameSite cookies.
- *Erroring with "open a LeetCode tab first":* rejected. The button worked from anywhere before this change; demanding a tab would be a user-visible regression caused purely by an internal fix. Auto-opening a background tab (closed again in a `finally`) preserves the old behaviour.
- *Erroring on a still-loading tab instead of polling:* the poll re-reads truth each tick, which `tabs.onUpdated` cannot — a listener registered before an `await` does not survive service-worker eviction.
- *Keeping `fetchImpl`'s default:* rejected. The default **was** the bug; leaving it would put the broken call one forgotten argument away from returning. Requiring it forces every caller to state which context the request runs in.

New `tabs*`/`scripting` wrappers went into `browser_api.ts` rather than calling `chrome.*` directly as the existing `chrome.tabs` calls do. Those are fire-and-forget, where Firefox's callback-only alias resolving to `undefined` is harmless; every call added here is awaited **for its return value**, so `await chrome.tabs.query(...)` on Firefox would resolve to `undefined` and report "no LeetCode tab" with one sitting right there.

Extension v1.2.4. 116 extension tests (up from 102), `addons-linter` clean on `dist-firefox/`.


## D-071 — NeetCode aliases onto the LeetCode catalog; no separate NeetCode catalog (2026-08-02, reverses D-064)

**Decision:** New `problem_aliases` table (`source`, `alias_slug` -> `problem_id`, plus `resolved_by`). A NeetCode solve resolves its slug to an **existing LeetCode `problems` row** and inherits that row's curated `problem_concepts` mapping. No `source='neetcode'` catalog rows are created; `import_neetcode_catalog.py` is deleted. New `backend/scripts/sync_neetcode_aliases.py` populates the table. `evidence.resolve_problem()` tries a native row for the source first, then the alias table.

**Why:** D-064 asserted NeetCode "has its own problem catalog, entirely separate from LeetCode's — different slugs, different problem text even for 'the same' interview question". The first half is true and the conclusion drawn from it was wrong. NeetCode's problems ARE LeetCode's problems, re-slugged: `two-integer-sum` is Two Sum, `duplicate-integer` is Contains Duplicate. Measured against the live catalog, not assumed:

```
NeetCode150 problems              588
  resolved to a LeetCode row      588  (100%)
      slug identical              514      no network call needed
      title match                  55      via getProblemMetadataFunctionHttp
      hand override                19      NeetCode renamed the problem itself
  landing on a mapped node        533  (90.6%)
  leetcode problems targeted >1x    0
```

Problem TEXT differing doesn't matter, because mastery attaches to the concept, not the prose — and the concept mapping is the expensive artifact. `problem_concepts` cost a curated LLM pass to build for LeetCode (`reviewed_by='pass3-blind:gemini-3.1-pro'`, 2828 problems). Aliasing inherits all of it and keeps inheriting it: the 55 resolved-but-unmapped problems are gaps in the LeetCode mapping itself, and fixing them there fixes NeetCode for free. A parallel catalog would have needed its own pass and then drifted from this one as each improved separately.

**Two bugs in the deleted importer, found while measuring** — it was never run against prod, so neither reached the DB. `getProblemListFunctionHttp` returns `name` for only 350 of 938 entries (absent on *every* NeetCode150 one), so `meta.get("name", slug)` would have titled 588 problems with their raw slug — "two-integer-sum", not "Two Sum". And it discarded `topics`, the per-problem LeetCode-style topic list, which is the only field in that response with any mapping signal. The docstring's documented response shape was simply wrong about both.

**Tradeoffs / rejected:**
- *Keeping the separate catalog and generating its `problem_concepts` by inheriting the matched LeetCode row's nodes:* rejected. Same 90.6% coverage, but it duplicates 588 rows that must then be kept in sync, and re-forks the moment either mapping is edited.
- *Fuzzy/embedding title matching for the last 15:* rejected in favour of a hand-listed `OVERRIDES` map. 15 entries is small enough to state exactly, and every target was confirmed present in the live catalog before being written down — a wrong alias is silently-wrong mastery on a real node, which is worse than leaving it unmapped. `resolve()` skips (with a warning) any override whose target is missing, so a stale entry degrades to unmapped rather than mis-mapped.
- *Aliasing NeetCode's ~350 non-problem entries* (SQL, Python For Beginners, ML, Design Patterns courses): out of scope — they have no LeetCode counterpart. Counted and reported by the sync, never silently dropped.
- *Idempotency:* `entity_id` is the resolved problem id and the dedupe index is `(user_id, source, entity_id)`, so solving Two Sum on both sites still records two events. Deliberate — `source` stays truthful about where the work happened.

**Still open:** there is no known way to read a user's NeetCode solve HISTORY. LeetCode's import works because `/api/submissions/` exists; NeetCode's equivalent sits behind the auth boundary this codebase cannot cross (it cannot create accounts). So NeetCode ingest is live-capture-forward only, with no backfill — logged to BACKLOG.
